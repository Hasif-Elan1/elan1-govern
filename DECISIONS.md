# Decisions

Where the brief was ambiguous, the simpler option was picked and noted here.

1. **`pnpm run setup`, not `pnpm setup`.** `pnpm setup` is a built-in pnpm command (it edits your shell profile) and cannot be overridden by a script. The one-command start is `pnpm run setup && pnpm dev`.
2. **A shared `packages/db`.** Both the web app and the gate service read the same tables, so the Prisma schema, the tenant helper `forOrg()` and the chain writer live in one package.
3. **One writer for the chain.** Only the gate service holds `GATE_MASTER_KEY`, which decrypts each org's Ed25519 key. The web app never signs anything: approvals, admin actions, rulebook publishing and org creation go through the gate service's internal API (HMAC-authenticated).
4. **One active key per org.** The org's active Elan1 Govern key signs receipts, checkpoints, evidence manifests and rulebooks. `govern sign` and `govern keygen` work with any key file, for teams that sign rulebooks offline and for tests. Keys can be rotated; retired keys are kept for verification (#33–#36).
5. **Receipt kinds.** Receipts carry a `kind`: `decision` (the guard's answer), `approval` (the second receipt of an ask), `outcome` (an SDK agent reporting what happened after `gate.check()`), `admin` (rulebook signed, connector added, role changed and so on).
6. **Privacy in summaries.** A receipt keeps display identifiers (bill id, vendor id, amount) and the values the rules inspected. For `to_domain_in` only the recipient's domain is kept, and for `fields_include` only the names of changed fields, never their values.
7. **Limits.** `daily_payments_inr` counts successful `zoho.record_bill_payment` calls since midnight IST. When a limit turns an allow into an ask, the first approver group in the rulebook approves it, with a 24h expiry. With no approver group it is refused.
8. **"Today" is India time** (Asia/Kolkata) for every org.
9. **Tenant isolation is enforced in code and in a test.** `forOrg(orgId)` is a Prisma client extension that ANDs `orgId` into every filter and sets it on every create. A test fails if any file outside `packages/db` touches a tenant model on the raw client.
10. **Versions.** Latest patches of majors with stable, well-known APIs: Next.js 15, React 19, Prisma 6, Zod 3, Vitest 3, ESLint 9, TypeScript 5.
11. **`APP_ENV`, not `NODE_ENV`, decides "production".** `next start` always sets `NODE_ENV=production`, so the check that refuses the `.env.example` sample secrets keys off `APP_ENV=production`.
12. **MCP refusals are tool results with `isError: true`**, carrying `structuredContent.gate = { decision, rule_id, reason }`. Agents (and LLMs) see tool errors; a JSON-RPC protocol error would hide the reason from the model.
13. **`gate.approval_status` is Elan1 Govern's own MCP tool**, not a connector tool. It only reads the calling agent's own approvals, so it is not governed by the rulebook. It long-polls up to 30 s.
14. **Approved MCP calls run on approval.** When an approver says yes, Elan1 Govern runs the held call immediately and writes the second receipt; the agent sees the result next time it asks. SDK checks are run by the agent, which then calls `record()`.
15. **Allowed actions run before their receipt is written** (as the brief orders it). If that write fails, the agent is refused and a health alert names the tool and the connector's reference, so a person can reconcile it. Every other path writes its receipt before anything runs.
16. **Mock connectors keep state in memory per org.** Restarting Elan1 Govern resets the demo mailbox and ledger. `pnpm demo` also resets them first (dev only), so it can be run again and again.
17. **Seed data.** `pnpm db:seed` creates `owner@demo.test` (owner) and `ca@demo.test` (approver) in Demo Traders, plus a second org, Patel Agro Foods, where the CA is an auditor, to show the client switcher. Both passwords are `DEMO_OWNER_PASSWORD`.
18. **The gate service runs with `tsx`** in dev and in Docker. That avoids a separate build step for a small service.
19. **Rate limits are in memory, per process.** Fine for one instance; several instances would need a shared store.
20. **Client IP for rate limits.** Forwarded headers are client-controlled unless a proxy sets them, so they are trusted only with `TRUST_PROXY=true`. Without it, all callers share one bucket per route (safe, coarser). Per-account login limits and lockout always apply.
21. **`RATE_LIMIT_MULTIPLIER`** raises per-IP limits for test runs from one machine. It is ignored when `APP_ENV=production`.
22. **Demo daily limit is ₹20,00,000**, not ₹5,00,000, so `pnpm demo` (₹2,18,000 per run) can be repeated many times a day. The rulebook in the brief is reproduced exactly in the core tests.
23. **Dependency versions moved for security.** zod 4, Vitest 4, nodemailer 10 and pnpm 10 (with a 7-day minimum release age, trust policy and an install-script allowlist) replaced older majors flagged by `pnpm audit` and semgrep.
24. **Sender domain on email receipts.** Reading an email records the sender's domain (e.g. `sharmatraders.in`), not the address, subject or body, so Activity is readable without storing personal data.
25. **Web routes are route handlers, not server actions.** Every write goes through one wrapper (`apps/web/src/server/api.ts`) that applies rate limits, CSRF, session, permission, fresh-sign-in and zod validation in a fixed order, and they can be tested over plain HTTP (the authz matrix).
26. **Auth is built in, not a library.** argon2id, sessions, lockout, TOTP and CSRF are ~300 lines with full tests. An auth library (Better Auth) is a candidate when SSO/SAML is added.
27. **SSO is OIDC with `openid-client`**, added to the existing auth instead of replacing it with an auth framework. One OIDC connection per org; domains count only after a DNS TXT proof, and only verified claims block other orgs, so nobody can squat a domain. SAML and SCIM are on the roadmap.
28. **Assessment templates are code, not rows.** The three built-in templates live in `packages/core/src/assessments.ts` with a version number; an assessment stores `templateKey` and `templateVersion`, so a later template change never rescores an old result. There is no `AssessmentTemplate` table until orgs need their own templates.
29. **Inventory values are strings, checked by zod.** `AiSystem` kind, stage, tier and data categories are plain string columns (no Prisma enums), with the accepted lists in `packages/core/src/inventory.ts`. Adding a value is a code change, not a migration. No relation fields were added to `Org` or `User`.
30. **Agents join the inventory lazily.** Creating an agent through the web app adds its system at once; the inventory page also adds any agent that has none (demo and seeded agents). A unique index on `(orgId, agentId)` keeps it idempotent. The starting tier is the agent's setup-question tier, and no `system.created` receipt is written for these, since `agent.created` already exists.
31. **The tier comes only from approved assessments.** People cannot set a system's risk tier or next review by hand. Approval sets the tier to the highest result among the latest approved assessment of each template, and the next review to 6 / 12 / 24 months for high / medium / low.
32. **Separation of duties is by user id.** The submitter (`submittedById`) can never review; the review update also filters on it, so two racing reviews cannot slip past. Approvers may draft and submit but not sign off; viewers and auditors only read.
33. **Inventory changes need a receipt or they are undone.** The web app makes the change, asks Elan1 Govern to sign the event, and reverts the change if Elan1 Govern cannot. A rare failure after the revert surfaces as a 500 with "Nothing was changed".
34. **Upstream tools start switched off.** A sync adds new tools disabled, with suggested tags, so nothing new reaches agents until a person has checked what each tool can do. Re-syncing keeps tags and on/off choices; tools the server no longer lists are deleted.
35. **Suggested tags come from the tool name**, by a fixed word list (`suggestTags` in core), and from the description only when the name matches nothing. Descriptions often say what a tool does *not* do ("never deletes"), which would mislead. Tags are suggestions; the person decides.
36. **Tool names are `<server>.<tool>`**, the server part derived from its name. `gate`, `gmail` and `zoho` are reserved so an upstream can never shadow a built-in tool. Upstream tool names that don't fit Elan1 Govern's tool-name pattern are skipped and counted.
37. **Unknown, disabled and removed tools are refused before any rule runs**, with rule id `default`, even if a rule still names them (rulebooks load leniently when a tool has gone away).
38. **One MCP session per upstream call.** Elan1 Govern connects, calls and closes each time (stateless). It costs a few extra requests but keeps no upstream state between calls or processes.
39. **Upstream errors are generic.** Agents, receipts and the console see "the MCP server reported an error" or an HTTP status, never the upstream's own error text, which can echo headers or personal data. Any echo of the stored auth header in a result is replaced with `[redacted]`.
40. **The registry is cached for 10 seconds per org** in the gate service and dropped on every upstream admin change, so a disabled tool stops working at once on the instance that changed it (and within 10 s on others).
41. **The auth header is one value, sent as `Authorization`.** It covers bearer tokens and API keys used as bearer tokens; servers that need other headers or OAuth are not supported yet. Only the URL's origin goes into receipts, since query strings can carry keys.
42. **`UPSTREAM_ALLOW_PRIVATE` defaults to on outside production**, so local MCP servers and tests work, and off with `APP_ENV=production`.
43. **The framework library is code, not data in the database** (`packages/core/src/frameworks`, imported as `@gate/core/frameworks`). It is pure TypeScript, used by the browser, the web server and the gate service, and unit-tested. It sits in core rather than a new workspace package so the lockfile did not need re-resolving. The per-org `Control` table (a seeded copy of the old 10 controls) was dropped; orgs only store which frameworks they turned on (`OrgFramework`). The migration turns on the five frameworks existing orgs already saw.
44. **Sources and the legal-review caveat.** Requirement references come from the official texts linked on each framework (EUR-Lex for the EU AI Act and GDPR, NIST AI 100-1, the ISO catalogue page for 42001, the DPDP Act as published by MeitY, the RBI FREE-AI committee report of August 2025, 45 CFR Part 164 via HHS, the AICPA 2017 Trust Services Criteria, Colorado SB 24-205, NYC Admin. Code §§ 20-870 to 20-874). References stop at the article, section, function or pillar where a finer citation was not certain; RBI FREE-AI is mapped at pillar level only. Summaries are one plain line written by us. Nothing claims compliance: every page and export says **Draft — needs legal review**. The RBI link points at rbi.org.in, not a deep link, because report URLs there change.
45. **Coverage** is requirements with at least one mapped control that has live evidence, divided by all requirements, rounded down. A requirement with no mapped control is a gap and is listed as such ("No control covers this yet"), not hidden.
46. **Inventory and assessment evidence come from receipts.** The controls "AI systems are inventoried" and "Risk assessments are approved before go-live" count receipts with action `system.created` and `assessment.approved`, so they work whether or not those features' tables exist.
47. **Industry packs use tag rules.** Starter rules target risk tags (`moves_money`, `deletes`, `sends_external`, `changes_production`, …), so they apply to any connector's tools. Money rules read a field named `amount`; a money tool without one matches no allow rule and is refused. The finance pack keeps the Gmail and Zoho Books demo rulebook (the demo agent's rulebook is generated from it). An org with no industry (created before packs) gets the finance pack.
48. **Wizard merge.** The add-agent wizard takes the risk-question suggestions for the pack's built-in tools, then adds the pack's rules and quotas (a suggestion wins on the same id). If the answers say the agent never moves money or never contacts outsiders, those rules become a tag refusal, so a broad "changes records" allow cannot let a payment through. High-risk agents ask before changing records. Every approver group the rules name gets the owner and the org's approvers.
49. **Framework report is a PDF from the gate service**, like the auditor pack: same fonts and layout code, all-time evidence counts, and an `evidence.exported` receipt. Industry and framework changes are written by the web app and receipted through the gate service's event endpoint (`org.industry_set`, `framework.enabled`, `framework.disabled`).

### Platform: jobs, webhooks, OpenAPI, key rotation

50. **Background jobs run on pg-boss** (`pg-boss@12.38.0`, MIT, Postgres-backed), not `setInterval`. Its tables live in their own schema (`JOBS_SCHEMA`, default `pgboss`), created on first start; Prisma migrations do not touch it. Three cron queues (`approvals-expire` every minute, `checkpoints-hourly` at :00, `webhook-sweep` every minute) are scheduled in the database, so pg-boss sends one job per tick however many Elan1 Govern instances run, and the `stately` queue policy allows at most one queued and one running job per cron queue, so a slow run is never doubled. `expireDue()`, `checkpointAll()` and `sweepWebhooks()` stay plain functions that tests call directly. Approval expiry moved from every 10 s to every minute; an approval past its time is still refused at once by `resolveApproval` and the long-poll, so the job only tidies up.
51. **Job logs are structured and PII-free**: queue name, duration and counts (`{ job, ms, expired }`), or for a webhook attempt the org, endpoint and delivery ids, event, attempt number, outcome and HTTP status. Never URLs, payloads, emails or secrets.
52. **Webhooks are enqueued after the receipt transaction commits.** The gate's one chain writer (`apps/gate/src/chain.ts`) collects the receipts a transaction wrote and, after commit, creates `WebhookDelivery` rows and pg-boss jobs in the background, so the guard never waits for subscribers and a rolled-back write sends nothing. If the process dies between commit and enqueue, that event is not sent (an outbox table written inside the transaction would close this gap at the cost of one more write per receipt; noted as a known limit). Retries are tracked on the delivery row, not by pg-boss, so Settings can show status, attempts and the last error: up to 8 attempts with backoff 30 s, 1, 2, 4, 8, 16, 32 minutes; a worker claims an attempt with a 60 s lease, so duplicate jobs are harmless. `webhook-sweep` re-sends anything due whose job was lost.
53. **Webhook body and signature.** The body is an envelope `{ id, type, created_at, org, data }`; for `receipt.created`, `data` is the receipt itself (already minimised, see #6). `approval.pending` and `approval.resolved` are derived from the same receipts. Headers: `gate-signature: t=<unix>,v1=<hex HMAC-SHA256 of "<t>.<body>">` (Stripe-style; receivers reject old timestamps to stop replays), `gate-event`, `gate-delivery` (an id for de-duplication). Secrets are 256-bit, shown once, stored AES-GCM-encrypted under the master key. The admin receipts `webhook.created` / `webhook.deleted` are written by the gate (not `WEB_EVENTS`) and name the URL's host only, because paths and query strings often carry tokens.
54. **SSRF protection for webhooks**: http(s) only, no credentials in the URL, no redirects followed, 10 s timeout, and the address is checked after DNS resolution, inside the socket's `lookup`, so the connection goes to exactly the address that was checked (no DNS-rebinding window). Private, loopback, link-local, CGNAT, multicast, documentation and reserved ranges (IPv4, IPv6 and IPv4-mapped IPv6) are refused unless `WEBHOOK_ALLOW_PRIVATE=true`, which defaults to true only when `APP_ENV` is not `production`, so local receivers work in development.
55. **OpenAPI is generated, not hand-written.** `apps/gate/src/openapi.ts` builds an OpenAPI 3.1 document from the same zod schemas the routes validate with (`z.toJSONSchema`, JSON Schema 2020-12), plus response and error shapes and the MCP endpoint (its tools in `x-mcp-tools`). It is served at `GET /v1/openapi.json` without auth and checked in at `docs/openapi.json`; a test fails if they drift (`pnpm --filter @gate/gate openapi` regenerates). Validation is a light structural check in the test, to avoid a heavy validator dependency.
56. **Signing keys can be rotated; `OrgKey` is the source of truth.** Each org has one active key and any number of retired ones, kept for verification. `kid` is the key's fingerprint, so verifiers recompute it rather than trust a label. The migration copies every `Org.publicKey`/`privateKeyEnc` into an `OrgKey` row (SQL, same fingerprint formula); the gate also copies it lazily on first use for any org row written by older code. The `Org` columns are left as the org's first key, for compatibility; nothing reads them once `OrgKey` rows exist. Keys copied from `Org` keep their original AES-GCM AAD (`org-key:<org>`); new keys use `org-key:<org>:<kid>`.
57. **How rotation works.** Under the org's chain lock: an admin receipt `key.rotated { old_kid, new_kid }` is written and signed with the OLD key, the old key is retired at that receipt's timestamp, the new key becomes active, and every rulebook is re-signed with the new key (a rulebook's hash does not cover its signature, so receipts citing it stay valid; a rulebook the old key had not signed is left alone, never laundered). Every chain write resolves its key after taking the lock, so a write waiting on a rotation signs with the new key. Receipts and checkpoints carry `kid` (hash-covered); receipts from before this change have none and verify against any key not yet retired at their time. A verifier rejects anything signed by a key after its retirement, and a `key.rotated` receipt retires the signing key within the chain itself, even if the key list says nothing. Rotation is owner-only and needs a sign-in within 10 minutes.
58. **Bundles carry every key.** `public_keys.json` maps kid → PEM; `public_key.pem` stays the current key (it signs the manifest) for older verifiers; the signed manifest lists each kid with its retirement time. Old bundles without kids or `public_keys.json` still verify unchanged.
59. **`KeyProvider` is the KMS seam.** The gate wraps and unwraps org keys through `KeyProvider { name, wrap, unwrap }` (`apps/gate/src/keys.ts`); today's implementation is the env master key with AES-256-GCM. A cloud KMS implementation calls the KMS Encrypt/Decrypt (or GenerateDataKey for envelope encryption) with `{ orgId, kid }` as encryption context, and its `name` is stored per key row, so keys wrapped by different providers can coexist while migrating. Signing still happens in the gate process; moving signing into an HSM (Ed25519 sign in KMS) would add a `sign()` method and is not done yet.
60. **The product is called Elan1 Govern.** Every name people see changed: screens, page titles, emails, PDFs, the authenticator label, docs and the CLI (`govern verify`; `gate` stays as an alias so old auditor packs and scripts still work). Internal names stay as they were: package names (`@gate/*`), the `apps/gate` folder, environment variables (`GATE_*`), cookies and the `gate-signature` webhook header. Renaming those would break existing installs and customer webhook code for no visible gain.

### Python SDK

61. **The Python SDK uses the standard library only** (`urllib.request`, `json`, `hmac`, `hashlib`), so installing it adds no third-party code to an agent's environment: no `requests` or `httpx` and their dependency trees to vet and keep patched, and nothing that can be swapped by a compromised release. The cost is a synchronous client; `guarded` runs it in a worker thread for `async` tools, which is enough at one check and one record per tool call. It lives in `packages/sdk-python` but is not a pnpm package (pnpm ignores folders without `package.json`), so the lockfile is unchanged. Tests use `unittest` and a fake service on `http.server`; CI runs them with the runner's preinstalled `python3` rather than a setup action. The build backend (setuptools) is needed only to build the package, not at run time.
62. **Same meanings as the TypeScript SDK, with stricter failure handling.** Fields are the TypeScript ones in snake_case; `wait_for_approval` long-polls in steps of at most 30 seconds and returns `pending` when its time is up. Where the TypeScript SDK passes an answer through, the Python one fails closed: a check answer without a known decision, an `allow` without a `check_id`, a network error, a timeout and any redirect all raise `GovernError` (status 0 when there was no usable answer). Redirects are refused because following one would resend the API key to another address. `verify_webhook` accepts exactly what `verifyWebhook` accepts (checked against a signature made by the TypeScript code); its argument order is `(header, body, secret)`.
63. **`guarded` decisions.** Arguments are sent by parameter name (`**kwargs` flattened). An `ask` raises `ApprovalPending` at once unless the caller passes `wait=True`, so an agent never blocks for minutes without choosing to. A person's rejection or an expired approval raises `Refused`, like a rule refusal. If the tool raises, `error` is recorded and the tool's exception is re-raised (even if recording failed). If the tool succeeded but recording failed, `RecordError` carries the result, because raising a plain error there could make the agent run a payment twice.

### Test on past actions (replay)

64. **A separate, encrypted replay store, not richer receipts.** Receipts stay minimal (hash, display identifiers, inspected values) because they are exported, sent to webhooks and kept for years. To replay a draft over real calls we need the full validated arguments, so the gate writes them to `ReplayCall`, AES-256-GCM encrypted with `GATE_MASTER_KEY` and AAD `replay-args:<org>:<seq>`, kept 30 days and purged hourly (`replay-purge`, pg-boss). The per-org `replayStore` switch is on by default because the feature is useless without history; switching it off deletes the rows. A row is written only after the call reached the rules (validated arguments exist); calls refused before that (paused agent, unknown tool, invalid arguments, no or untrusted rulebook) are not stored and count as "could not be judged". The write is best-effort and outside the receipt transaction: a failed write is logged by error code and never changes the answer.
65. **Replays run in the gate service.** Only the gate has the master key. The web route (`POST /api/rulebooks/:slug/replay`, permission `rulebooks:publish`) forwards the draft YAML over the existing HMAC-signed internal API; the gate parses it against the org's registry (unsigned is fine: nothing is executed or published), decides each stored call again and returns counts plus up to 200 changed calls. Descriptions come from the receipt summary, so the answer never contains stored arguments. No receipt is written for a replay: it changes nothing.
66. **Replay is a pure function in core** (`replayRulebook`), so its rules are property-tested: replaying the active rulebook over its own history reproduces every decision, quotas included, and the counts always add up. Quota usage is built up in time order per quota window ("day" in the org's time zone, or rolling). What counts: a replayed allow counts if it ran then, or if it was not allowed then (nothing had failed); a replayed ask counts only if it was an ask then and a person approved it (we cannot know whether someone would approve a new ask); refusals never count. Everything not being replayed (other agents' calls, calls before the period, calls without stored arguments) counts as its receipt recorded it, using the receipt's summary for sums. Approximations: an approved call is counted at the time it was asked, not when it ran; a sum quota on a field the old rulebook did not inspect sees 0 for calls that are not replayed; rolling windows look back at most 90 days.
67. **Rate limits for replays**: 10 a minute per address and per org in the web app, 6 a minute per org in the gate, at most the 50,000 most recent calls per run. Periods are 7 or 30 days only, matching the store's retention.
68. **No new permission.** Testing on past actions uses `rulebooks:publish`: the people who can change rules are the ones who need to see their effect, and it keeps the authz table unchanged. `startOfDayIn` moved to core (the db package re-exports it) so the guard and the replay share one definition of "today".

### Approvals in Slack and WhatsApp

69. **Chat is a doorbell, not a replacement.** Slack and WhatsApp only tell approvers that something is waiting and, for low-impact rules, carry an Approve/Reject button. The rule, the decision, the receipt and the audit trail stay in Elan1 Govern, and every chat decision goes through the same `resolveApproval` as the web app (one atomic claim on the approval row, so double clicks and replays decide once). Email still goes out as before.
70. **`approve_in_chat` is per ask rule, off by default, and refused where it is risky.** Publishing (`publishProblems` → `chatApprovalProblems` in core, for every risk tier) refuses it on any rule that reaches, by tool or by tag, a tool tagged `deletes`, `changes_access`, `changes_production` or `personal_data`, or `moves_money` without an upper amount (`lt`/`lte` on a field named `amount` or `amount_*`). A tag rule is judged by every tool that has the tag today, plus the tag itself. The guard checks again when it holds the action (`chatApprovalAllowed`, against the current registry, since tags can change after publishing) and stores the answer on the approval as `chatApproval`; `resolveApproval` refuses a Slack or WhatsApp decision when it is false. Asks caused by a quota are never chat-approvable.
71. **Chat approval skips the password re-check.** The web app asks for the password if the last sign-in was more than 10 minutes ago; a chat button cannot. That is why chat approval is limited to rules that cannot delete, change access or production, touch personal data, or move uncapped money, and why it must be turned on rule by rule.
72. **Who clicked.** Slack users are matched to members only by an email Slack marks as confirmed (`users.info` with `users:read.email`; `is_email_confirmed` must be true; bots and deactivated users never match), then the usual checks (member of this org, approver role, named in the rule's group). If Slack does not report the flag, nobody can approve from Slack, which fails closed. Clicks whose `team.id` is not the connected workspace are ignored. WhatsApp senders must match a number the member verified with a 6-digit code (HMAC-stored, 10 minutes, 5 tries, 3 codes per 15 minutes).
73. **One URL per connected channel.** Each org's Slack app and WhatsApp number get their own inbound URL (`/chat/slack/<id>/interactions`, `/chat/whatsapp/<id>/webhook`), so the gate knows which signing secret to check before reading anything. Inbound requests are acknowledged at once (Slack wants an answer within 3 seconds) and decided in the background; replies go back as a Slack ephemeral message (`chat.postEphemeral`) or a WhatsApp text, never through a `response_url` taken from the payload.
74. **What is recorded.** The approval row stores `channel` (`web`, `email`, `slack`, `whatsapp`) and `channelUser`; the approval receipt carries the same in `details` (`channel`, `channel_user`). `details` was chosen over new fields on `approval` because older `govern verify` builds parse receipts strictly and would reject unknown approval fields; `details` is already a free-form object. Slack users are recorded as `team/user`; WhatsApp users as `wa:` plus 16 hex of a keyed hash of the number. Numbers are stored AES-GCM-encrypted (needed to send), with a keyed hash to match replies and the last four digits for display; receipts and logs never contain them, and Meta error text (which can echo a number) is reduced to its numeric code.
75. **Sending is a pg-boss job with its own retry rows (`ChatMessage`),** like webhook deliveries: 6 attempts with the webhook backoff, permanent errors (bad token, unknown channel, outside Meta's 24-hour window) fail at once, the `webhook-sweep` cron also re-sends lost chat jobs. A message is written after the approval commits, so the guard never waits. After any decision or expiry (web, email, chat or the expiry job) the Slack message is updated to show the outcome and lose its buttons; a post that is still queued when the approval is decided is skipped.
76. **Outbound hosts are fixed.** The only hosts called are `SLACK_API_URL` and `WHATSAPP_API_URL`, which must be `https://slack.com/…` and `https://graph.facebook.com/…` when `APP_ENV=production` (checked at start-up; other values exist for the fake servers in tests). Paths that would leave the base are refused, redirects are not followed, calls time out after 10 s. No SDKs: plain `fetch`, so no new dependencies.
77. **WhatsApp templates.** Business-initiated messages outside Meta's 24-hour window need approved templates. One optional approval template (body `{{1}}` action, `{{2}}` rule, `{{3}}` expiry; two quick-reply buttons whose payloads Elan1 Govern sets per approval) and one optional authentication template for the code. Without them, interactive and text messages are sent, which Meta delivers only inside the window. App-only approvals are sent as a plain text with the link (no template), so outside the window those rely on email; a second "link" template could be added later.
78. **Settings.** Channels live under **Settings → Notifications** (`notifications:manage`, owners and admins, with a sign-in in the last 10 minutes). Secrets are write-only and never shown again; the WhatsApp webhook verify token is shown once and stored as a SHA-256 hash. Approvers add their own number on the same page (`approvals:decide`). Connecting and disconnecting writes `chat.connected` / `chat.disconnected` receipts; verifying or removing a number writes `chat.number_verified` / `chat.number_removed` with the hashed id only.

### Rule suggestions learned from approvals

79. **Suggestions are mined from approvals, by a pure function in core** (`mineSuggestions` in `packages/core/src/suggest.ts`). Its input is the agent's active rulebook and its resolved approvals, using only each approval's stored argument summary (the values the rules inspected plus display identifiers) and its timestamps. Nothing new is stored on receipts or approvals for it. Only ask rules that name one tool are considered; tag rules, rules that already have an exception, and tools tagged `deletes`, `changes_access` or `changes_production` are skipped.
80. **Rules can have an exception, `unless`, on ask rules only.** With strictest-wins and no negation in conditions, an allow rule can never beat an ask rule that also matches, so turning part of an ask into an allow needs a way to narrow the ask. `unless` takes the same conditions as `when`; the ask stands aside only when every one holds, and a missing value never holds, so a malformed call still waits for a person. The schema rejects `unless` on allow and refuse rules, so a refuse can never carry an exception. Receipts record the values exceptions look at, like any condition. Where a simple threshold is enough (the demo's `pay-small`/`pay-large` pair), the draft moves the threshold and uses no exception.
81. **The thresholds.** At least 10 approvals the draft would allow, spread over at least 7 days, the latest in the last 14, out of a 30-day look-back. Nothing in the allowed group was rejected or expired: the cap is set below the smallest amount that was, at most the largest approved amount, rounded down to two significant figures (₹98,750 becomes ₹98,000), and below any refuse threshold on the same field. A counterparty list holds values seen at least twice and never rejected or expired, at most 25. Counterparty-only drafts are not made for tools that move money; there a cap is always part of the rule. One suggestion per ask rule: the one that would have allowed the most approvals, and on a tie the narrower one (cap and counterparties).
82. **Every draft is replayed before it is shown.** Each past approval of the agent is decided again against the current and the drafted rulebook (rebuilding `to` from `to_domain` and `fields` from field names). The draft is dropped unless every changed decision is an ask that became an allow for an approval a person approved. It must also validate against the org's tool registry and pass the high-risk publish checks for the agent's tier.
83. **"Applying" means opening a draft.** There is no stored-draft table: the builder's draft lives in the browser until it is signed. Applying marks the suggestion `applied`, writes a `suggestion.applied` receipt, and sends the person to `/rulebooks/<agent>?suggestion=<id>`, where the builder starts from the suggestion's drafted rulebook (kept on the `RuleSuggestion` row). Publishing is the existing signed flow and needs `rulebooks:publish`. A draft made from an older rulebook version is refused, so a stale suggestion can never overwrite a newer rulebook. A new permission, `suggestions:manage` (owners and admins, the people who edit rulebooks), opens and dismisses; everyone can read them.
84. **Dedupe and dismissal.** Suggestions are stored per (org, agent, kind, fingerprint), the fingerprint being the sha256 of the kind, tool, rule and the drafted rules. Each run updates matching open ones, leaves applied ones alone, and deletes open ones the evidence no longer supports. A dismissed suggestion, or any later draft of the same kind for the same rule, stays hidden until the approvals behind it have at least doubled and grown by at least 10 since it was dismissed (`evidenceGrewEnough`). Dismissals are receipted (`suggestion.dismissed`).
85. **Time saved** is the approvals the draft would have allowed, scaled to 30 days over the period since the first of them (at least 7 days), plus their median time from asking to an answer. It is an estimate: quotas can still turn an allowed action into an ask.
86. **The job.** `rule-suggestions-nightly` runs on pg-boss at 02:00 India time (`30 20 * * *` UTC) for every org and logs only a count; one org's failure raises a health alert and does not stop the rest. "Look for suggestions" runs the same code for one org at once.
87. **Demo history.** Receipts cannot be backdated (the chain records real time), so `pnpm db:seed` (and a dev-only gate route the end-to-end test uses) adds a month of resolved payment approval rows for the demo AP agent and one admin receipt, `demo.history_added`, saying so. The history (41 payments from ₹52,000 to ₹1,00,000 to six vendors, all approved, plus one larger payment rejected and one expired) fits the demo rulebook, so exactly one suggestion appears: raise the no-approval limit from ₹50,000 to ₹1,00,000.

### Unusual-behaviour alerts, auto-pause and the emergency stop

88. **Detectors are pure functions over an agent's own decision receipts** (`packages/core/src/behaviour.ts`). The baseline is the last 14 days. Volume uses robust statistics: the median and median absolute deviation of calls per *active* hour (hours with no calls are left out, or an office-hours agent would look like a spike all day), with the spread never taken as less than √median because counts are roughly Poisson. The last hour is a rolling 60 minutes compared with clock-hour buckets.
89. **"Seen before" looks back 90 days** for tools and counterparties, so a monthly vendor is not "new" every month, while the volume, refusal and amount baselines use 14 days. Counterparties come only from display identifiers receipts already hold (`vendor`/`vendor_id`, `to_domain`, `payee`, `account`, `customer`), grouped so a vendor's name and id count as the same kind of thing. A sender domain on an email the agent *read* is not a counterparty.
90. **Learning is days since the agent's first decision** (default 7, per org 0 to 30), not active days, so it is easy to explain. No alert of any kind during learning.
91. **Default severities.** New tool: low. New counterparty: medium when the action carries an amount, otherwise low. Off-hours: low, medium at 10+ calls. Volume, refusal surge and amount: medium or high by threshold. Only high alerts can auto-pause, so a new vendor never stops an agent on its own.
92. **The inline check runs after commit, in the background**, hooked into the gate's one chain writer for decision receipts (so it covers the guard and nothing else needs changing). The call has already been decided and answered; a failure becomes a `behaviour-check-failed` health alert. Calls refused because the agent is paused are skipped, so an emergency stop does not produce a refusal storm of alerts, and the 5-minute job skips paused agents.
93. **The 5-minute job is one pg-boss cron queue (`behaviour-scan`, stately) that walks every org**, each in its own try/catch like the hourly checkpoints, and only looks at agents that acted in the last hour. Fanning out a job per org was not needed at this scale.
94. **Deduplication.** `dedupeKey = agent|detector|key` is set while an alert is open or acknowledged and cleared on resolve, with a unique index on `(orgId, dedupeKey)` (a partial index is not expressible in the Prisma schema, and a hand-written one would be dropped by the next `migrate dev`). A repeat updates the open alert (occurrences, last seen, receipts). A finding whose receipts an earlier alert already covered is not raised again, so resolving an alert does not bring it straight back on the next scan.
95. **Acknowledge vs resolve.** Owners, admins and approvers do both (approvers already act on risky actions); viewers and auditors read. Acknowledged alerts still block a duplicate; resolved ones do not.
96. **Alert receipts are written by "Elan1 Govern"** as the actor, inside the same transaction as the alert row (and, with auto-pause, the agent's status), so an alert never exists without its receipt. The `alert.created` webhook payload is derived from that receipt, like the approval events.
97. **Emergency stop is one chain transaction**: pause every active agent, create the `Incident` with the ids it paused, and write one `emergency.stop` receipt with the count. Only one stop can be open. Resume starts only those ids that are still paused, so agents paused before the stop, or auto-paused or paused by hand during it, stay paused. Both need owner/admin, a fresh sign-in and (to stop) the typed word `STOP`; the console shows a red banner on every page while it lasts.
98. **The incident report is a PDF from the gate service**, reusing the evidence PDF writer, covering an hour before the stop to the resume (or now): the story, who, alerts, every receipt (up to 300 rows) and the receipt range plus the IST dates to export a bundle for `govern verify`. Its download is logged as `evidence.exported` and needs `evidence:export`.
99. **The seeded demo shows a real alert.** The seed does a little ordinary work with the demo agent while it is learning, then sets the demo org's learning period to 0 (receipted) and pays Nilgiri Office Supplies, a vendor the agent has never paid, through the normal guard. The "New vendor" alert comes from the same inline check as in production; nothing is back-dated or written by hand.

### SAML 2.0, "Require SAML for everyone" and SCIM

100. **SAML 2.0 with `@node-saml/node-saml` 5.1.0**, next to OIDC (decision 27), not an auth framework. One SAML connection per org (`SamlConnection`): the IdP's entity id, sign-in URL and signing certificates (up to three, for key rolls), and our SP entity id, which defaults to the metadata URL `/api/auth/saml/metadata?org=<id>` and is unique across orgs. Only SP-initiated sign-in: `POST /api/auth/saml/start` sends an AuthnRequest with the HTTP-Redirect binding; the answer comes back with HTTP-POST to the one ACS, `POST /api/auth/saml/acs`. IdP-initiated (unsolicited) responses are refused: without a request to answer, login CSRF and replay are much harder to stop. Encrypted assertions, signed AuthnRequests and single logout are not supported yet. 5.2.0 was newer than the 7-day minimum release age when this was written.
101. **What an answer must pass.** The assertion itself signed by a stored certificate (always required; a signed response around an unsigned assertion is not enough; xml-crypto reads only the signed content); `InResponseTo` on the response and the subject confirmation equal to the request id kept in the AES-GCM, httpOnly flow cookie (10 minutes); `NotBefore`/`NotOnOrAfter` within 2 minutes of skew, and no older than 10 minutes since `IssueInstant`; audience = our SP entity id; issuer = the IdP entity id; the request id and the assertion id unused (`SamlReplay`, one row each, kept until the assertion could no longer be accepted, purged on each sign-in); the email (an email attribute, else an emailAddress NameID) inside a verified domain of the org.
102. **The ACS is the one cross-site POST.** `route()` has a `crossSitePost: "saml-acs"` option, allowed only on public routes without a JSON body, that skips the same-origin and CSRF-token checks for that route alone; the signed assertion, `InResponseTo` the cookie's request id, and the one-time assertion id authenticate it instead. For the cookie to come back on the IdP's cross-site form POST it is `SameSite=None; Secure` (httpOnly, path `/api/auth/saml`, 10 minutes, deleted on first use) when cookies are secure; on plain-http dev it is `Lax`, which works because a local IdP on another localhost port is same-site. A form-post landing page was the alternative; it adds a page and an extra round trip for no extra safety, since the cookie alone proves nothing without a signed answer to it. The session cookie stays `Lax`. The ACS answers with a 303 redirect.
103. **Verified domains are shared between OIDC and SAML.** `SamlConnection` has its own `domains`, `verifyToken` and `verifiedDomains`, checked with the same DNS TXT proof (`gate-verify=<token>`, reusing the OIDC token when the org has one), and an org's verified domains are the union of both connections'. `domainClaimedElsewhere` looks at both, so a domain still belongs to at most one org.
104. **Just-in-time accounts.** On (`jit`, the default) a first SAML sign-in creates the account (with an unusable `!saml:` password) and a membership with the connection's default role, which can never be Owner (refused at save, and mapped to viewer in code). Off, only existing members get in. Existing memberships keep their role. A person the directory deactivated (SCIM `active=false`) is not added back by SAML or OIDC sign-in.
105. **"Require SAML for everyone"** (`enforced`) refuses password sign-in for any address in the org's verified domains before the password is looked at, so a refused attempt reveals nothing about the password and counts no failure. Every refusal writes an `auth.refused` receipt (actor: the address tried; details: `saml_required`, `password`) through the gate events route; if the gate service cannot write it, the attempt is still refused and the miss is logged. Break-glass: the org's owners with two-step sign-in may still use a password (and their code), so the org is never locked out when its IdP is down, and each such sign-in writes `auth.break_glass`. Requiring SAML is refused unless SAML is on, a domain is verified and at least one owner has two-step sign-in. The emergency-access grants approved by a second person that the console shows are not part of this slice.
106. **Who manages it.** Saving SAML, verifying its domains and issuing a SCIM token use `sso:manage` (owners) with a fresh sign-in for the first and last, not owners and admins: whoever controls the IdP or the SCIM token can sign in or remove anyone in the verified domains, owners included, so an admin who could change them could make themselves an owner. Owners and admins can read the settings (`GET /api/settings/saml`). Every change writes `identity.updated` or `identity.scim_token_rotated`, and is undone if the receipt cannot be written.
107. **SCIM 2.0, Users only** (RFC 7643/7644), at `/api/scim/v2/Users` and `/Users/{id}`, plus `ServiceProviderConfig`. Machine endpoints: not `route()`, no session, cookies or CSRF; each request carries the org's bearer token (`scim_…`, 256 bits, shown once, stored as a SHA-256 hash; rotating replaces it at once), which names the org. Rate limits: 300 requests a minute per address, checked before the token, and 600 a minute per org. Supported: list with `userName eq "…"` and paging, create, get, PUT, PATCH (`add`/`replace`/`remove` on `active`, `displayName`, `externalId`; Entra's `"False"` strings accepted; other attributes ignored), DELETE. Not supported: Groups (and group-to-role mapping), Bulk, sorting, ETags, other filters.
108. **What SCIM may do.** Create (or link an existing account and membership; an existing membership keeps its role) only for emails in the org's verified domains, with the token's default role, never Owner or Auditor. `active=false` removes the membership, which ends all access at once (every request re-reads memberships), and keeps the `ScimUser` row and the role so `active=true` restores it; DELETE removes the membership and the row but not the account, which may belong to other orgs. Owners are never deactivated or removed by the directory (403): only owners touch owners. Directory changes are receipts `scim.user_provisioned`, `scim.user_deactivated`, `scim.user_reactivated` and `scim.user_removed` by the actor `scim@directory.invalid`, with the role but no email, like other member receipts; a change whose receipt cannot be written is undone.
