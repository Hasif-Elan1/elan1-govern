# Decisions

Where the brief was ambiguous, the simpler option was picked and noted here.

1. **`pnpm run setup`, not `pnpm setup`.** `pnpm setup` is a built-in pnpm command (it edits your shell profile) and cannot be overridden by a script. The one-command start is `pnpm run setup && pnpm dev`.
2. **A shared `packages/db`.** Both the web app and the gate service read the same tables, so the Prisma schema, the tenant helper `forOrg()` and the chain writer live in one package.
3. **One writer for the chain.** Only the gate service holds `GATE_MASTER_KEY`, which decrypts each org's Ed25519 key. The web app never signs anything: approvals, admin actions, rulebook publishing and org creation go through the gate service's internal API (HMAC-authenticated).
4. **One active key per org.** The org's active Gate key signs receipts, checkpoints, evidence manifests and rulebooks. `gate sign` and `gate keygen` work with any key file, for teams that sign rulebooks offline and for tests. Keys can be rotated; retired keys are kept for verification (#33–#36).
5. **Receipt kinds.** Receipts carry a `kind`: `decision` (the guard's answer), `approval` (the second receipt of an ask), `outcome` (an SDK agent reporting what happened after `gate.check()`), `admin` (rulebook signed, connector added, role changed and so on).
6. **Privacy in summaries.** A receipt keeps display identifiers (bill id, vendor id, amount) and the values the rules inspected. For `to_domain_in` only the recipient's domain is kept, and for `fields_include` only the names of changed fields, never their values.
7. **Limits.** `daily_payments_inr` counts successful `zoho.record_bill_payment` calls since midnight IST. When a limit turns an allow into an ask, the first approver group in the rulebook approves it, with a 24h expiry. With no approver group it is refused.
8. **"Today" is India time** (Asia/Kolkata) for every org.
9. **Tenant isolation is enforced in code and in a test.** `forOrg(orgId)` is a Prisma client extension that ANDs `orgId` into every filter and sets it on every create. A test fails if any file outside `packages/db` touches a tenant model on the raw client.
10. **Versions.** Latest patches of majors with stable, well-known APIs: Next.js 15, React 19, Prisma 6, Zod 3, Vitest 3, ESLint 9, TypeScript 5.
11. **`APP_ENV`, not `NODE_ENV`, decides "production".** `next start` always sets `NODE_ENV=production`, so the check that refuses the `.env.example` sample secrets keys off `APP_ENV=production`.
12. **MCP refusals are tool results with `isError: true`**, carrying `structuredContent.gate = { decision, rule_id, reason }`. Agents (and LLMs) see tool errors; a JSON-RPC protocol error would hide the reason from the model.
13. **`gate.approval_status` is Gate's own MCP tool**, not a connector tool. It only reads the calling agent's own approvals, so it is not governed by the rulebook. It long-polls up to 30 s.
14. **Approved MCP calls run on approval.** When an approver says yes, Gate runs the held call immediately and writes the second receipt; the agent sees the result next time it asks. SDK checks are run by the agent, which then calls `record()`.
15. **Allowed actions run before their receipt is written** (as the brief orders it). If that write fails, the agent is refused and a health alert names the tool and the connector's reference, so a person can reconcile it. Every other path writes its receipt before anything runs.
16. **Mock connectors keep state in memory per org.** Restarting Gate resets the demo mailbox and ledger. `pnpm demo` also resets them first (dev only), so it can be run again and again.
17. **Seed data.** `pnpm db:seed` creates `owner@demo.test` (owner) and `ca@demo.test` (approver) in Demo Traders, plus a second org, Patel Agro Foods, where the CA is an auditor, to show the client switcher. Both passwords are `DEMO_OWNER_PASSWORD`.
18. **The gate service runs with `tsx`** in dev and in Docker. That avoids a separate build step for a small service.
19. **Rate limits are in memory, per process.** Fine for one instance; several instances would need a shared store.
20. **Client IP for rate limits.** Forwarded headers are client-controlled unless a proxy sets them, so they are trusted only with `TRUST_PROXY=true`. Without it, all callers share one bucket per route (safe, coarser). Per-account login limits and lockout always apply.
21. **`RATE_LIMIT_MULTIPLIER`** raises per-IP limits for test runs from one machine. It is ignored when `APP_ENV=production`.
22. **Demo daily limit is ₹20,00,000**, not ₹5,00,000, so `pnpm demo` (₹2,18,000 per run) can be repeated many times a day. The rulebook in the brief is reproduced exactly in the core tests.
23. **Dependency versions moved for security.** zod 4, Vitest 4, nodemailer 10 and pnpm 10 (with a 7-day minimum release age, trust policy and an install-script allowlist) replaced older majors flagged by `pnpm audit` and semgrep.
24. **Sender domain on email receipts.** Reading an email records the sender's domain (e.g. `sharmatraders.in`), not the address, subject or body, so Activity is readable without storing personal data.
25. **Web routes are route handlers, not server actions.** Every write goes through one wrapper (`apps/web/src/server/api.ts`) that applies rate limits, CSRF, session, permission, fresh-sign-in and zod validation in a fixed order, and they can be tested over plain HTTP (the authz matrix).
26. **Auth is built in, not a library.** argon2id, sessions, lockout, TOTP and CSRF are ~300 lines with full tests. An auth library (Better Auth) is a candidate when SSO/SAML is added.

### Platform: jobs, webhooks, OpenAPI, key rotation

27. **Background jobs run on pg-boss** (`pg-boss@12.38.0`, MIT, Postgres-backed), not `setInterval`. Its tables live in their own schema (`JOBS_SCHEMA`, default `pgboss`), created on first start; Prisma migrations do not touch it. Three cron queues (`approvals-expire` every minute, `checkpoints-hourly` at :00, `webhook-sweep` every minute) are scheduled in the database, so pg-boss sends one job per tick however many Gate instances run, and the `stately` queue policy allows at most one queued and one running job per cron queue, so a slow run is never doubled. `expireDue()`, `checkpointAll()` and `sweepWebhooks()` stay plain functions that tests call directly. Approval expiry moved from every 10 s to every minute; an approval past its time is still refused at once by `resolveApproval` and the long-poll, so the job only tidies up.
28. **Job logs are structured and PII-free**: queue name, duration and counts (`{ job, ms, expired }`), or for a webhook attempt the org, endpoint and delivery ids, event, attempt number, outcome and HTTP status. Never URLs, payloads, emails or secrets.
29. **Webhooks are enqueued after the receipt transaction commits.** The gate's one chain writer (`apps/gate/src/chain.ts`) collects the receipts a transaction wrote and, after commit, creates `WebhookDelivery` rows and pg-boss jobs in the background, so the guard never waits for subscribers and a rolled-back write sends nothing. If the process dies between commit and enqueue, that event is not sent (an outbox table written inside the transaction would close this gap at the cost of one more write per receipt; noted as a known limit). Retries are tracked on the delivery row, not by pg-boss, so Settings can show status, attempts and the last error: up to 8 attempts with backoff 30 s, 1, 2, 4, 8, 16, 32 minutes; a worker claims an attempt with a 60 s lease, so duplicate jobs are harmless. `webhook-sweep` re-sends anything due whose job was lost.
30. **Webhook body and signature.** The body is an envelope `{ id, type, created_at, org, data }`; for `receipt.created`, `data` is the receipt itself (already minimised, see #6). `approval.pending` and `approval.resolved` are derived from the same receipts. Headers: `gate-signature: t=<unix>,v1=<hex HMAC-SHA256 of "<t>.<body>">` (Stripe-style; receivers reject old timestamps to stop replays), `gate-event`, `gate-delivery` (an id for de-duplication). Secrets are 256-bit, shown once, stored AES-GCM-encrypted under the master key. The admin receipts `webhook.created` / `webhook.deleted` are written by the gate (not `WEB_EVENTS`) and name the URL's host only, because paths and query strings often carry tokens.
31. **SSRF protection for webhooks**: http(s) only, no credentials in the URL, no redirects followed, 10 s timeout, and the address is checked after DNS resolution, inside the socket's `lookup`, so the connection goes to exactly the address that was checked (no DNS-rebinding window). Private, loopback, link-local, CGNAT, multicast, documentation and reserved ranges (IPv4, IPv6 and IPv4-mapped IPv6) are refused unless `WEBHOOK_ALLOW_PRIVATE=true`, which defaults to true only when `APP_ENV` is not `production`, so local receivers work in development.
32. **OpenAPI is generated, not hand-written.** `apps/gate/src/openapi.ts` builds an OpenAPI 3.1 document from the same zod schemas the routes validate with (`z.toJSONSchema`, JSON Schema 2020-12), plus response and error shapes and the MCP endpoint (its tools in `x-mcp-tools`). It is served at `GET /v1/openapi.json` without auth and checked in at `docs/openapi.json`; a test fails if they drift (`pnpm --filter @gate/gate openapi` regenerates). Validation is a light structural check in the test, to avoid a heavy validator dependency.
33. **Signing keys can be rotated; `OrgKey` is the source of truth.** Each org has one active key and any number of retired ones, kept for verification. `kid` is the key's fingerprint, so verifiers recompute it rather than trust a label. The migration copies every `Org.publicKey`/`privateKeyEnc` into an `OrgKey` row (SQL, same fingerprint formula); the gate also copies it lazily on first use for any org row written by older code. The `Org` columns are left as the org's first key, for compatibility; nothing reads them once `OrgKey` rows exist. Keys copied from `Org` keep their original AES-GCM AAD (`org-key:<org>`); new keys use `org-key:<org>:<kid>`.
34. **How rotation works.** Under the org's chain lock: an admin receipt `key.rotated { old_kid, new_kid }` is written and signed with the OLD key, the old key is retired at that receipt's timestamp, the new key becomes active, and every rulebook is re-signed with the new key (a rulebook's hash does not cover its signature, so receipts citing it stay valid; a rulebook the old key had not signed is left alone, never laundered). Every chain write resolves its key after taking the lock, so a write waiting on a rotation signs with the new key. Receipts and checkpoints carry `kid` (hash-covered); receipts from before this change have none and verify against any key not yet retired at their time. A verifier rejects anything signed by a key after its retirement, and a `key.rotated` receipt retires the signing key within the chain itself, even if the key list says nothing. Rotation is owner-only and needs a sign-in within 10 minutes.
35. **Bundles carry every key.** `public_keys.json` maps kid → PEM; `public_key.pem` stays the current key (it signs the manifest) for older verifiers; the signed manifest lists each kid with its retirement time. Old bundles without kids or `public_keys.json` still verify unchanged.
36. **`KeyProvider` is the KMS seam.** The gate wraps and unwraps org keys through `KeyProvider { name, wrap, unwrap }` (`apps/gate/src/keys.ts`); today's implementation is the env master key with AES-256-GCM. A cloud KMS implementation calls the KMS Encrypt/Decrypt (or GenerateDataKey for envelope encryption) with `{ orgId, kid }` as encryption context, and its `name` is stored per key row, so keys wrapped by different providers can coexist while migrating. Signing still happens in the gate process; moving signing into an HSM (Ed25519 sign in KMS) would add a `sign()` method and is not done yet.
